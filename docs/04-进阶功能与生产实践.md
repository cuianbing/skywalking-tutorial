# 第 4 篇 · 进阶功能与生产实践

> 前提：第 3 篇的两个演示服务已在运行。本篇把 SkyWalking 从"能看到链路"用到"团队日常排障 + 生产可运维"：UI 深入使用、自定义埋点、日志关联 TraceId、告警、采样、数据保留策略与生产部署建议。

---

## 一、UI 功能深入导览

以 10.x 内置 UI 为例（Horizon UI 布局略有不同，功能对应）：

| 页面 | 入口 | 用途 |
| --- | --- | --- |
| 服务看板 | General Service → Service | 每个服务的调用量、平均/分位响应时间、SLA、实例数；Java 服务还有 JVM 页签（堆、GC、线程、CPU） |
| 拓扑图 | Topology | 全局服务依赖图；点边上数字看该调用边的 QPS/耗时/错误率；区分 General（应用）/ Mesh（Service Mesh）等层 |
| 实例对比 | 服务 → Instance | 同一服务多实例的负载是否均衡、某个实例是否有慢查询 |
| 端点分析 | 服务 → Endpoint | 每个 URI 的调用量/耗时/错误率，慢接口排名 |
| 链路查询 | Trace | 按服务/端点/时长/错误状态/tag/TraceId 检索，详情页看 Span 树 + 瀑布图 + Tag + 异常堆栈 |
| 日志 | Log | 若接了日志上报（第三节），可按服务/TraceId 查日志 |
| 告警 | Alerting | 告警历史与规则命中的指标快照 |
| 性能剖析 | 服务 → Profile | 对慢端点做方法级 CPU 采样（无需改代码），定位"代码里哪一行慢" |

**排查一次线上慢请求的推荐动线**：

```text
Topology 发现某条调用边错误率高/耗时长
  → Trace 按该服务 + 错误状态过滤，找出慢/错 Trace
  → 打开 Span 树定位到具体 Exit Span（SQL / 下游调用 / MQ）
  → 结合该 TraceId 搜业务日志（含上面打的 [%tid]）
  → 还不够？Profile 对该端点采样，看方法级热点
```

## 二、自定义埋点：@Trace / TraceContext

自动埋点覆盖的是"通用组件"，业务自定义方法（如一个核心定价算法）默认不在链路里。Toolkit 提供注解级埋点，先加依赖：

```xml
<dependency>
    <groupId>org.apache.skywalking</groupId>
    <artifactId>apm-toolkit-trace</artifactId>
    <version>9.8.0</version>
</dependency>
```

> 这个依赖只提供注解与 API 壳，真正逻辑由探针在运行时注入：**不挂 agent 时程序照常运行**（返回空值），所以不会污染本地开发。

```java
import org.apache.skywalking.apm.toolkit.trace.Tag;
import org.apache.skywalking.apm.toolkit.trace.Trace;
import org.apache.skywalking.apm.toolkit.trace.TraceContext;

public class PriceService {

    // 在方法上打一个 Local Span，命名并带业务 Tag
    @Trace(operationName = "计算折扣")
    @Tag(key = "userId", value = "arg[0]")
    @Tag(key = "grade", value = "arg[1]")
    public BigDecimal calcDiscount(String userId, String grade, BigDecimal price) {
        // TraceContext 可取当前链路 ID，写进业务对象或日志
        String traceId = TraceContext.traceId();
        // TraceContext.putCorrelation("bizOrder", orderId); // 跨进程传递业务键
        return doCalc(price);
    }
}
```

要点：

- `@Tag` 的取值支持 `arg[0]`（第 1 个入参）、`arg[0].field`（入参字段）、`returnedObj.field`（返回值字段）；
- `TraceContext.traceId()`：当前请求的 TraceId，**未被采样时可能返回空串**；
- `@Trace` 加的是 Local Span，天然跟随所在服务的调用链。

### 异步线程：@TraceCrossThread

线程池里执行的任务默认会"断链"（新线程丢失链路上下文）。Toolkit 的解法是在任务类上标注解：

```java
import org.apache.skywalking.apm.toolkit.trace.TraceCrossThread;

@TraceCrossThread
public class RiskCheckTask implements Callable<Boolean> {
    private final String orderId;
    public RiskCheckTask(String orderId) { this.orderId = orderId; }

    @Override
    public Boolean call() throws Exception {
        // 风控校验逻辑；此 Span 会正确挂到发起调用的那条 Trace 上
        return check(orderId);
    }
}

// 使用
executor.submit(new RiskCheckTask(orderId));
```

注意：注解打在**实现类上**，匿名内部类/lambda 无法生效；这是官方为异步场景提供的标准方案。

## 三、日志关联：让每行日志带上 TraceId

两件事：**① 本地日志打印 TraceId（排障靠它 grep 全链路）；② 把日志上报到 SkyWalking（UI 链路详情里直接看）**。以 logback 为例。

加依赖：

```xml
<dependency>
    <groupId>org.apache.skywalking</groupId>
    <artifactId>apm-toolkit-logback-1.x</artifactId>
    <version>9.8.0</version>
</dependency>
```

`logback.xml`：

```xml
<appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
        <!-- 用 SkyWalking 的 layout 才支持 %tid -->
        <layout class="org.apache.skywalking.apm.toolkit.log.logback.v1.x.mdc.TraceIdMDCPatternLogbackLayout">
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%tid] [%thread] %-5level %logger{36} - %msg%n</pattern>
        </layout>
    </encoder>
</appender>

<!-- 上报到 OAP 的 appender（走 gRPC，与探针同通道） -->
<appender name="SW_GRPC" class="org.apache.skywalking.apm.toolkit.log.logback.v1.x.log.GRPCLogClientAppender">
    <encoder>
        <layout class="org.apache.skywalking.apm.toolkit.log.logback.v1.x.mdc.TraceIdMDCPatternLogbackLayout">
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%tid] %-5level %logger{36} - %msg%n</pattern>
        </layout>
    </encoder>
</appender>

<root level="INFO">
    <appender-ref ref="CONSOLE"/>
    <appender-ref ref="SW_GRPC"/>
</root>
```

效果：

- 控制台/文件日志变成 `2026-11-11 10:00:00.123 [3f2a...e91] INFO  c.d.a.OrderController - 订单已支付`——`[%tid]` 未接入时打印 `TID: N/A`，接入后自动替换为真实 TraceId；
- UI 的 **Trace 详情 → 相关日志** 能看到这条链路的所有日志；Log 页也能按 TraceId 搜索。

log4j2 同理（`apm-toolkit-log4j-2.x` + `TraceIdLog4j2Layout`），此处不展开。

## 四、告警：把"人盯大盘"变成"系统找人"

编辑 OAP 的 `config/alarm-settings.yml`，重启 OAP 生效。规则语义是：**每 `period` 分钟检查一次窗口，窗口内 `count` 次命中阈值就触发，触发后 `silence-period` 个周期内不再重复告警**。

```yaml
rules:
  service_resp_time_rule:
    metrics-name: service_resp_time     # 服务平均响应时间（ms）
    op: ">"
    threshold: 1000
    period: 10
    count: 3
    silence-period: 5
    message: "服务 {name} 平均响应时间超过 1000ms"

  service_sla_rule:
    metrics-name: service_sla           # 成功率（万分比，8000 = 80%）
    op: "<"
    threshold: 8000
    period: 10
    count: 2
    silence-period: 5
    message: "服务 {name} 成功率低于 80%"
```

通知渠道：

```yaml
# 通用 Webhook：告警时 POST 一段 JSON 给你的服务，再自由转发到钉钉/企微/电话
webhooks:
  - http://127.0.0.1:9999/alarm/receive

# 新版本内置钉钉、企业微信、Slack、PagerDuty 等 hook，alarm-settings.yml 里有注释模板可抄
```

验证：给 service-b 加个开关让接口慢 2 秒，几分钟后 Alerting 页应出现告警记录，并命中你的 webhook。

## 五、采样与探针开销

流量大时的三个旋钮（都在 `agent/config/agent.config` 或 `-D` 覆盖）：

| 旋钮 | 默认 | 建议 |
| --- | --- | --- |
| `agent.sample_n_per_3_secs` | `-1`（全采样） | 高流量服务设为每 3 秒 N 条（如 100）；**指标/拓扑/告警不受采样影响**，只影响链路明细存储量 |
| `agent.ignore_suffix` | 常见静态资源后缀 | 补齐自家静态资源/健康检查路径，减少噪音 |
| 插件裁剪 | `plugins/` 全启用 | 用不到的中间件插件可删 jar，减少类增强次数 |

关于开销：探针是字节码增强 + 异步批量上报，官方定位为低开销；但每个系统的业务形态不同，**上线前用生产级压测对比开关探针前后的 P99 与 CPU** 是标准动作。另外别把采样率和日志全量上报同时拉满，存储才是最先扛不住的。

## 六、数据保留（TTL）：数据存多久

10.2+ 把 BanyanDB 的连接与保留策略放在 `config/bydb.yaml`。默认 TTL（关键项）：

| 数据 | 默认保留 | 对应环境变量 |
| --- | --- | --- |
| 链路 Trace | 3 天 | `SW_STORAGE_BANYANDB_TRACE_TTL_DAYS` |
| 日志 | 3 天 | `SW_STORAGE_BANYANDB_LOG_TTL_DAYS` |
| 分钟级指标 | 7 天 | `SW_STORAGE_BANYANDB_METRICS_MINUTE_TTL_DAYS` |
| 小时/天级指标 | 15 天 | `SW_STORAGE_BANYANDB_METRICS_HOUR_TTL_DAYS` / `..._DAY_...` |

"为什么昨天的链路查不到了？"——先看 TTL。修改方式：改 `bydb.yaml` 里对应 `ttl`（或用环境变量覆盖），重启 OAP；**只对新写入数据生效**。指标是降采样聚合的，即使明细过期，天/小时级趋势仍在，这也是"指标存 7~15 天够用"的原因。

## 七、生产部署建议

1. **存储选型**：中小规模（几十个服务以内）默认 BanyanDB 单机即可；超大规模或已有 ES 运维团队时选 Elasticsearch/OpenSearch（最吃资源但生态成熟）。别用 MySQL 存大规模链路。
2. **OAP 高可用**：默认 `standalone`；生产上 OAP 是无状态服务，通过 `cluster` 模块（K8s / ZooKeeper / Consul / Etcd 等 provider）组成集群水平扩展，前置一个负载均衡把 11800 暴露给探针。
3. **UI 与安全**：UI 走 Nginx 反代并加企业 SSO/鉴权；**禁止 11800/12800 暴露公网**。若用 11.x，admin-server（17128）默认无鉴权，务必用网关 IP 白名单包住。
4. **版本与插件管理**：agent 包统一放公司制品库（Nexus/内部 HTTP），各服务用同一版本；升级 agent 先在预发环境验证插件兼容性（尤其框架大版本升级时）。
5. **Kubernetes 部署**：官方提供 Helm Chart（`skywalking-helm`）与 Swck Operator，Java 应用可以用 initContainer 方式注入 agent（参照官方 "deploy agent in k8s" 文档）。
6. **监控 OAP 自己**：开启 self-observability（telemetry 选 Prometheus）+ 对 OAP 本身配告警，避免"监控系统先挂了没人知道"。

## 八、FAQ

**Q1：`@Trace` 加了但 UI 上没有这个 Span？**
确认三点：依赖是 `apm-toolkit-trace`（不是别的同名类）；agent 已挂载；该类在运行期由 JVM 加载（不是反射绕过）。Toolkit 注解需要探针的 activation 生效，本地没挂 agent 跑单测时看不到是正常的。

**Q2：日志上报了，UI 的 Trace 里却看不到日志？**
检查 `SW_GRPC` appender 是否挂进了 root logger；OAP 侧日志接收默认开启，若改过 `application.yml` 的 `receiver-log` 确认没被禁用。

**Q3：告警一直不触发？**
理解 `period` + `count` 的语义：`period: 10, count: 3` 表示连续 10 分钟一个窗口内 3 次超阈值——低频偶发问题不会触发，这是防抖设计。指标名以 UI 指标字典为准（如 `service_resp_time` 单位 ms、`service_sla` 单位万分比）。

**Q4：UI 时间和本地差 8 小时？**
OAP 用系统时区，容器部署时给容器设置 `TZ=Asia/Shanghai`。

**Q5：链路只有 3 天数据？**
默认 TTL（见第六节），不是丢数据，是保留策略。按合规与排障需求调大，注意磁盘成本。

**Q6：想看"每个 SQL 语句"的耗时？**
JDBC 插件会记录 SQL（Tag 里 `db.statement`），但注意生产上 SQL 全量记录有敏感信息风险，可在探针侧配置插件参数或依赖采样兜底。
